# SquareSumV1 S03M–S03O 性能优化设计

日期：2026-08-07

目标平台：Ascend 910B，CANN 社区版 8.5.0

比赛目标：所有正确性测试通过，不按隐藏样例硬编码，将正式稳定中位耗时降至 `0.30 × 3985.330 = 1195.599 μs` 以内。

## 1. 已确认的事实

- 用户给定基准 S02BA 为 `3985.330 μs`；目标上限为 `1195.599 μs`。
- 当前历史正式最好版本是 S02F：`3223.995 μs`。
- S03J、S03K 的公开矩阵曾获得显著局部加速，但正式成绩分别为
  `3259.544 μs`、`3277.140 μs`，没有命中正式评分的主要耗时路径。
- S03L 以正式失败的 S03K 为源码基线，S02F 到 S03L 累计包含 816 行
  变化，因此携带 S03J/S03K 的退化风险。
- S03L 的控制证据中最大回退为 `7.283%`、最大基线漂移为 `5.465%`，
  但结果文件仍标记 `passed=true`。现有门禁不能作为提交依据。
- 当前公开规格域中仍有两个明确的未覆盖瓶颈：奇数最内归约约
  `2.08 ms`，inner 不对齐约 `3.02 ms`。
- 比赛读取 `msprof` 的 Task Duration：30 次算子调用，排除
  `aclnnMul`，按 `[10:30]` 取中位数。NPU Event 只能用于快速筛选，
  不能用于候选晋级。

## 2. 设计原则

1. 所有新候选都从具有正式成绩的可追溯基线构建，不继续叠加已失败候选。
2. 每一阶段只改变一种通用执行结构，保持来源、收益和回退可归因。
3. 路由只能使用公开的 shape、axis、stride、dtype、容量和硬件约束，禁止
   使用 Case 编号、隐藏尺寸常量或评分结果分支。
4. 正确性、路由边界、UB 容量、DMA 参数和 TilingKey 注册必须先通过，
   再运行性能门禁。
5. 性能晋级以比赛同口径 `msprof` A/B/A 为准，不能用 Event 数值替代。
6. 未通过阶段门禁的代码不得进入下一阶段、正式 ZIP 或 submission-src。

## 3. 分阶段架构

### 3.1 S03M：从 S02F 干净移植相邻保留行分组路径

S03M 从冻结的 S02F 源码独立建立，只移植 S03L 的 fastPath4 key 7：

- Host 识别物理相邻的保留输出行；
- 按 8、4、2 行选择分组宽度；
- 将多个短 GM→UB 搬运合并为一次连续搬运；
- 在 UB 内平方并沿最后一个归约维做树形规约；
- 对更外层归约组累计部分和；
- 一次向量写回同组输出；
- 其他输入严格回退 S02F。

干净移植只包含以下六类改动：Host 路由、任务调度、Kernel 模板开关、
`ProcessStridedGroupedRows`、幂次行归约辅助函数、key 7/CMake 注册。
S03J/S03K 的 fastPath2 改动不进入 S03M。

S03M 首轮仍限定：inner 以 8 对齐、最后归约维为 2 的幂、UB 容量合法、
任务数足以覆盖核心。这样可以先验证 key 7 本身在干净基线上的真实收益。

### 3.2 S03N：支持任意最后归约长度

S03N 只能建立在通过全部 S03M 门禁的源码上。它移除“最后归约维必须为
2 的幂”的限制，使用幂次块分解处理任意正长度：

1. 将行数分解为从大到小的 2 的幂块；
2. 每个块继续使用原有向量树归约；
3. 将各块结果累加到独立的 FP32 输出累加区；
4. 尾块不读取越界元素，也不依赖填充值参与求和；
5. FP16、BF16、FP32 保持题目要求的平方和输出语义。

S03N 不修改 inner 对齐规则。奇数、质数以及 `2^k±1` 是主要边界，
但路由对所有合法任意长度通用。

### 3.3 S03O：支持 inner 不对齐

S03O 只能建立在通过全部 S03N 门禁的源码上。它解决每个归约子行不是
32 字节对齐时的布局问题：

- 计算 dtype 对应的 `alignedInner`；
- 使用二维 DMA 将每个逻辑归约子行搬入按 32 字节对齐的 UB 行；
- padding 仅存在于 UB，不改变 GM 的逻辑索引；
- 平方、树归约和累加均使用 `alignedInner` 作为 UB stride；
- 写回只包含真实 inner 元素；
- 对 blockCount、src/dst stride、rightPadding 和 UB 总容量做显式上界检查；
- 超出指令或容量边界时回退上一阶段实现。

该路径优先减少逐输出、逐归约行的小 DMA 和标量同步。实现不得假设某个
隐藏维度，只依赖连续物理布局及公开约束。

## 4. 数据流与回退

Host 先使用现有元数据得到 fastPath、输出/归约维和输入 stride，再按
`S03O → S03N → S03M → S02F` 的能力顺序选择最专用且合法的路径。
每条新路径必须在 Host 和 Kernel 中使用一致的任务数、分组宽度、行距和
TilingKey。任何溢出、零维、UB 超限、DMA 参数超限或布局不满足，都回退到
已验证的上一层路径；不得让 Kernel 在运行中静默返回而丢失输出。

计算数据流为：GM 输入 → 分组/对齐搬入 UB → 按输入 dtype 完成平方语义 →
FP32 向量树归约 → 外层归约组累加 → 转回输出 dtype → 连续写回 GM。

## 5. 验证设计

### 5.1 静态与构建验证

- 校验 S03M 相对 S02F 的差异只包含批准的 key 7 代码；
- 校验所有 Host 可选 TilingKey 均在 Kernel CMake 中注册；
- 校验任务覆盖无重复、无遗漏，尾组不跨保留行边界；
- 校验所有乘加使用防溢出计算；
- 校验 UB、blockCount、stride、padding、mask 和 repeat 上界；
- 从干净源码构建并独立安装 `.run`。

### 5.2 正确性验证

每阶段运行既有全量套件，并增加该阶段边界矩阵：

- FP16、BF16、FP32；
- 单轴、多轴、负轴、无序轴、`keep_dims`；
- rank 2–5、单例维间隔和等价物理布局；
- 分组维 `1/2/3/7/8/9/15/16/17/31/32/33`；
- 最后归约维 `1/2/3/7/8/9/31/32/33/63/64/65/127/128/129`；
- inner `1/2/7/8/9/15/16/17/31/32/33/63/64/65/127/128/129/199/200`；
- 输入规模、归约规模、任务数和 UB 容量门槛的前一点、临界点和后一点。

任一错误、编译告警转错误、入口缺失、设备异常或超时均淘汰当前阶段。

### 5.3 性能验证

每阶段使用同一构建环境执行 Baseline/Candidate/Baseline：

- S03M 基线固定为 S02F；S03N 基线为通过的 S03M；S03O 基线为通过的 S03N；
- 每点使用比赛同构的 30 次调用和 `msprof Task Duration`；
- 解析器必须发现预期的 30 个 `aclnnMul` 和 30 个 SquareSumV1 任务；
- 覆盖题面范围内 fast1/2/3/4、三 dtype、对齐/非对齐和控制路径；
- 目标路径每点至少改善 50%；
- 任一控制路径回退不得超过 3%；
- 两次基线漂移不得超过 3%；
- 不满足门禁时不打包、不提交正式平台。

Event A/B 可用于决定是否值得启动完整 `msprof`，但不能改变上述门禁。

## 6. 产物与可追溯性

每个通过阶段独立保存：

- `candidates/squaresum_<版本>_<方向>_20260807/` 源码快照；
- 机器可读的正确性、路由、A/B/A 与 `msprof` 结果；
- 云端验证报告和正式提交 ZIP；
- ZIP、RUN、Host、Kernel、CMake 的 SHA-256；
- 正式平台返回的五个 Case 原始结果。

`submission-src/SquareSumV1` 只更新为最近一个通过全部内部门禁的版本。
正式历史最好仍以平台结果决定；内部候选不得冒充正式基线。

## 7. 完成标准

S03M、S03N、S03O 是逐级候选，不是目标终点。只有当正式平台五个 Case
全部通过，稳定中位耗时不高于 `1195.599 μs`，且代码符合比赛规则、没有
隐藏样例硬编码时，本轮总目标才算完成。若 S03O 后仍未达标，保留所有
证据并继续从正式最好版本分析其他未覆盖通用路径，不降低目标。
